# Издательская система для «Вестника НГУ»

Наша команда представляет издательскую систему для журнала «Вестник НГУ», серия «Информационные технологии». Система заменяет действующий сайт журнала и ведёт статью от подачи до публикации. Журнал выходит только в электронном виде.

Система предназначена для редакции, которой приходится вручную подбирать рецензентов, отслеживать десятки статей в разных состояниях и готовить вёрстку. Она должна убрать два главных узких места: простои из-за рецензентов, которые не отвечают, и очередь на вёрстку. За основу берётся платформа OJS: мы разворачиваем её, настраиваем под процесс редакции и дорабатываем там, где штатных средств недостаточно.

## Путь статьи

Статья проходит по цепочке: **автор → секретарь → член редколлегии → рецензент → собрание редколлегии**.

1. Автор подаёт рукопись через личный кабинет. Обязательные поля проверяет форма подачи.
2. Секретарь видит все поступившие статьи и распределяет их по портфелям членов редколлегии по тематике.
3. Член редколлегии вникает в статью. Слабую или бессмысленную статью он может отклонить сразу, без рецензирования. Иначе он выбирает рецензента (по умолчанию одного) из пула.
4. Рецензент присылает рецензию. Если член редколлегии с ней не согласен, он отправляет статью другому рецензенту.
5. Член редколлегии выносит статью на собрание редколлегии.
6. Собрание принимает решение: принять или отклонить. Слабую или спорную рецензию оно может отправить на дополнительную рецензию.
7. Принятая статья проходит подготовку к публикации и выходит в журнале.

Оба возврата (несогласие с рецензией и дополнительная рецензия) ведут к члену редколлегии: следующего рецензента всегда выбирает человек.

## Основные возможности системы

- **Подача и допуск** - автор загружает рукопись в формате Word (DOCX) или LaTeX, заполняет метаданные и тематику через личный кабинет. Допустимые форматы указаны автору явно, остальные запрещены. Обязательные поля проверяет форма подачи, возврата автору за формальные ошибки нет: на входе статью только допускают к рассмотрению или отклоняют.
- **Роли секретаря и члена редколлегии** - секретарь видит все статьи и список членов редколлегии и раскладывает статьи по портфелям. В журнале секретарь не научный работник, поэтому он должен сразу видеть, о чём статья; рецензентам он статьи не отправляет. Член редколлегии видит только свой портфель, «ничего лишнего».
- **Теги и пул рецензентов** - теги есть у статей, членов редколлегии и рецензентов. Система предлагает теги, человек подтверждает: секретарь подтверждает теги при распределении, член редколлегии может их поправить. Рецензенты хранятся в пуле, найденные люди больше не забываются и доступны для повторных приглашений. Из пула система предлагает около 10 подходящих кандидатов и показывает, почему они рекомендованы; выбирает всегда член редколлегии, он же может добавить рецензента вручную.
- **Число рецензентов** - по умолчанию один, член редколлегии может добавить ещё столько, сколько нужно. Число жёстко не фиксируется, так как в разных областях принято по-разному.
- **Контроль рецензирования** - рецензенту, не ответившему на приглашение, система напоминает по схеме 7/14/21: напоминание через неделю, второе через две недели, на 21-й день рецензенту уходит вежливое письмо об отказе от его участия и приглашение снимается. Статья передаётся другому рецензенту, которого выбирает член редколлегии.
- **Сводный экран** - секретарь видит состояние всех статей журнала, член редколлегии видит состояние статей своего портфеля: этап, ответственного, ближайший срок, время на этапе и следующее действие. Статьи с нарушенными сроками выделяются, из списка можно сразу перейти к нужному действию.
- **Собрание редколлегии и решение** - решение по статье принимает собрание редколлегии, а не один редактор. Система хранит список статей к собранию и фиксирует принятые решения. По итогам собрания статья может быть направлена на дополнительную рецензию. После принятия решения автор получает его через систему.
- **Работа через личный кабинет и уведомления** - подачи по почте нет. Автор получает письмо при каждой смене статуса статьи.
- **Доработка автором** - автор присылает новую версию и ответ на замечания, после чего начинается новый раунд рецензирования.
- **Вёрстка** - после литературного редактирования принятая рукопись преобразуется по цепочке DOCX → LaTeX → JATS XML, из исходника собирается PDF. Результат автоматической конвертации считается черновиком, до идеала доводить его не нужно. Проверяющий видит рядом исходник, LaTeX и скомпилированный PDF: ошибки находят по PDF. XML проверяется на соответствие схеме, ошибки попадают в отчёт.
- **Проверка орфографии и пунктуации** - система только подсвечивает возможные ошибки, автоматически ничего не исправляет, потому что слово может оказаться термином. Формулы не затрагиваются.
- **Согласование и публикация** - автору уходит PDF в журнальном виде, автор подтверждает его. Статья публикуется по готовности в текущий номер; по сроку номер закрывается и открывается следующий. Решение о публикации принимает редколлегия.
- **Статистика** - общая статистика по журналу сохраняется. Дорабатывается после запуска и по запросу редакции.

## В процессе разработки нам предстоит

- развернуть OJS 3.5.0-x (без обновления до 3.6) и настроить его под процесс редакции: роли секретаря и члена редколлегии, портфели, схему переходов, слепое рецензирование;
- реализовать то, чего нет в OJS: справочник тегов и предложение тегов, пул рецензентов и подсказку кандидатов, подсказку секретарю по распределению статей, схему напоминаний 7/14/21 с вежливым отказом и снятием приглашения, этап собрания редколлегии;
- сделать конвертацию DOCX → LaTeX → JATS XML отдельным сервисом (Pandoc и XeLaTeX в своём контейнере), связанным с OJS плагином-коннектором, поскольку штатно OJS выдаёт JATS с пустым телом; настроить проверку полученного XML и сборку PDF;
- перенести архив старого сайта;
- подготовить инструкцию по развёртыванию и начать обучение сотрудников редакции;
- перевести редакцию на новую систему и вывести из эксплуатации старый сайт.

### Технические решения

- Теги хранятся в плагине отдельно от ключевых слов автора. Мастер подачи OJS не меняем.
- К декабрю предложение тегов строится по словарю с синонимами (название, аннотация, ключевые слова). После декабря словарь можно заменить локальной моделью эмбеддингов. Внешний LLM по API используется только с согласия редакции.
- Окружение: OJS 3.5.0-x, MariaDB 10.11, Docker Compose, общий Google-аккаунт для почты, эталонная база с настройками журнала в git.

## Что будет готово к декабрьскому показу и MVP

Главный результат: через систему можно провести статью от подачи до публикации:

- **Платформа:** OJS на сервере, роли секретаря и члена редколлегии, почта, кнопка конвертации в карточке статьи, резервные копии.
- **Теги и подбор:** справочник тегов, предложение тегов с подтверждением человеком, до 10 кандидатов из пула для члена редколлегии.
- **Сроки и процесс:** новая диаграмма и требования, напоминания 7/14/21 с вежливым отказом, страница секретаря для распределения статей.
- **Конвертация:** DOCX или LaTeX в LaTeX, PDF и JATS XML как черновик, безопасная компиляция, таблица результатов на 3–5 реальных статьях.

Система также должна стать основой для дальнейшего развития. Возможные расширения:

- поддержка других серий журнала на той же платформе;
- доступ по nsu id;
- контроль редакционного процесса, в том числе более развитый контроль задержек;
- возможность редактировать файлы в веб-интерфейсе системы;
- подбор рецензентов и теги на основе эмбеддингов, а при согласии редакции и LLM.

Результатом проекта станет работающий сайт журнала с реальной вёрсткой и подбором рецензентов.
